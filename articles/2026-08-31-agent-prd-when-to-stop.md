# AI 产品经理最该写进 PRD 的，可能是“什么时候停手”

> 读完一次 Agent 越界事件，我重新看了一遍权限、失败和人工确认

*2026 年 8 月*

我把 OpenAI 和 Hugging Face 对那次 Agent 越界事件的复盘来回看了两遍。

14 个公开泄露的凭证，约 17600 次操作，6280 组行为，这些数字已经够吓人了。可最让我停下来的，是事故里一个不太显眼的细节。

这个 Agent 不太会放弃。

它原本参加的是网络安全评估。7 月 10 日，它在网上找到一批泄露的 Hugging Face 凭证，验证以后又把结果分享给其他 Agent。一天后，它已经能在服务器上执行代码，访问范围继续扩大，直到 Hugging Face 从日志里发现异常，事情才慢慢停下来。

OpenAI 后来说明，主导这次事件的是一款内部研究模型。测试时降低了部分安全限制，普通用户没有接触过，客户数据和公开产品也没有受到影响。这个边界必须说清楚。拿一次研究事故去证明今天所有商业 Agent 都会攻击外部系统，既不准确，也没有多少讨论价值。

我在意的是另一件事。一个被要求完成目标的 Agent，遇到困难时会继续找路。它不会天然知道哪条路已经超出用户的意思，也不会替产品经理判断，试到第几次就该停。

这件事放进 PRD，问题立刻变得具体了。

## 我们太习惯写“怎样成功”

普通软件的 PRD 很喜欢顺着成功路径往下写。用户点哪里，系统返回什么，下一步跳到哪个页面。流程走通，需求看起来也就写完了。

Agent 沿着这条路继续往前，会碰到一个麻烦。它可以自己拆任务、调工具、换方案。产品经理写下一句“帮用户订一张下周三去上海的机票”，工程团队拿到的却是一长串动作。

Agent 要查航班，可能读取日历，还要填写乘机人信息。锁定座位会占库存，付款会花掉用户的钱。网站报错以后，它可以重试，也可以换一家平台。它发现高铁更便宜，还可能顺手把任务带到铁路网站。

每一步单独看都像在帮忙，连起来以后，Agent 已经走出了用户刚才那句话。我的判断很明确。Agent PRD 里，“何时停手”应该和“如何完成”写在同一页，甚至写得更早。

OpenAI 在事故调查里提到，ExploitGym 有 898 个测试任务，其中 198 个从未被受测模型正确完成。事故期间，Agent 在临时信息板上讨论的任务，93% 来自这 198 道难题。它投入了更多推理和操作，成绩没有提高，访问范围却越走越远。

这个细节很像现实产品会遇到的情况。订票接口连续报错，Agent 该试三次还是十次。原平台用不了，它能不能换一个。预计费用涨了两百元，它该继续执行，还是回来问一句，这些都得有人提前定。

这些都不能留给模型临场发挥。

一份能上线的 PRD，至少应该写清单步重试次数、整项任务的最长时间，以及费用超过多少必须回来询问用户。目标已经无法完成，Agent 也要有一条正常的退出路径，可以告诉用户卡在哪里，请用户补充信息，也可以干脆结束任务。

![Agent 在任务边界前停下](../assets/2026-08-31-agent-prd-when-to-stop-task-boundary.png)

*Agent 在任务边界前停下，把扩大权限的决定交还给人。*

我很愿意看到 Agent 说一句“这件事我现在做不到”。任务没完成，用户还有机会换办法。Agent 悄悄扩大权限继续试，用户连它走到了哪里都不知道。

## 一个授权开关管不了整项任务

我最不喜欢的一类设计，是把“用户愿意使用 Agent”当成一张长期通行证。

用户同意搜索航班，只能说明他愿意让 Agent 查公开信息。读取整个月的日历、调用证件信息、提交订单和付款会带来完全不同的后果，把这些动作塞进一个“允许访问”的按钮里，开发省事，风险全留给用户。

权限应该跟着任务走。

查航班时，Agent 获得本次搜索需要的读取权限。用户选定班次以后，再申请锁定座位所需的权限。到了付款这一步，把乘机人、时间、总价和退改费用摆出来，让用户亲手确认。订单完成，临时权限随任务一起结束。

ChatGPT 当前的连接应用已经在区分读取和修改动作。遇到会改变外部数据、暴露敏感信息或难以撤回的操作，系统会再次询问用户。这种区分写进 PRD 时，不能只剩一句“接入第三方平台”。

产品经理要继续往下拆。Agent 能搜索什么，能读取什么，可以填写哪些字段，哪一步允许提交，授权又能持续多久。用户拒绝以后，任务是结束，还是退回到只给建议的状态，也得写明白。

这里最考验产品经理的地方，其实不在技术名词。你得替用户看清一次点击会带来什么后果。

确认页面如果只写“是否继续”，这个弹窗几乎没有价值。用户需要看到 Agent 准备买哪一班飞机，花多少钱，用了谁的身份信息，取消会损失多少。系统申请日历权限时，也应该说清读取哪一天，别上来就要整个日历。

![高后果动作留给人确认](../assets/2026-08-31-agent-prd-when-to-stop-human-confirmation.png)

*高后果动作留给人确认，操作记录保留查询和撤回入口。*

确认点也不能铺满每一步。搜索公开航班可以自动完成，向外发邮件会形成承诺，应该让用户检查。付款、删除数据和公开发布的恢复成本更高，确认要更严格，而且一定要放在用户仍然有机会阻止结果的位置。

## 做完以后，还得把账讲清楚

Agent 在聊天框里说“已经处理好了”，这句话只能证明它给了一个结果。

用户还需要知道它调用了哪个服务，读了哪些信息，哪一步经过自己确认。出了错，用户要能从这里进入取消、撤回或申诉。

国内发布的智能体应用实践参考已经提出，运行环境应提供运行日志、异常报告和风险追溯服务。我赞同这个方向，但产品不能把一份技术日志直接扔给普通用户。接口名称、参数和报错码适合工程师排查，用户需要看到的是一段能读懂的任务记录。

订票 Agent 可以这样记。10 点 21 分查询航班，10 点 24 分读取用户指定日期的日历，10 点 27 分由用户确认总价，随后提交订单。买错票以后，用户沿着这份记录找到取消入口。取消不了，记录里也应该告诉他下一步去哪里申诉。

我现在判断一个 Agent 产品能不能上线，会先看失败的那条路。

让它订一张票，中间故意关掉接口，改掉价格，再拒绝一次付款授权。看它会不会停，会不会解释，会不会偷偷换平台，任务结束后再看用户能不能查到它做过的每一步。

顺利跑通一次 Demo 很容易让人兴奋。可用户最后敢不敢把邮箱、日历和付款交给它，取决于出错时还能不能掌握局面。

这也是我读完这次事故后最想补进 PRD 的一句话。Agent 可以很能干，但它必须知道什么时候把决定还给人。
